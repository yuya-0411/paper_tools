# paper_tools

`paper_tools` は，論文の構成，本文，助言，AI向けプロンプト，Typstソースをブラウザー内で作成・保存する静的Webアプリである．Python，Node.js，パッケージインストール，ビルド，ローカルサーバーは不要である．既定は端末内保存で，必要な場合だけSupabaseのログインと端末間同期を追加できる．

## すぐに使う

### PC上で使う

1. リポジトリをZIPでダウンロードして展開する．
2. ルートの `index.html` をダブルクリックする．
3. ブラウザーで論文プロジェクトを作成する．

環境構築コマンドはない．`index.html` を開いた時点で利用を開始できる．

## 主な機能

- 5段階の新規作成画面と，目的別の組込みテンプレート．
- Markdown，TXT，JSON，Typst，LaTeX，HTMLテンプレートのアップロード，自動解釈，登録．
- 4項目だけで始められる簡易入力と，実験条件・評価指標まで扱う詳細入力．
- 入力済みの事実だけを使う決定論的な草稿生成と，不足情報・図・表・評価データ・実験・引用の診断．
- 章の追加・改名・並べ替え・削除と，各章の論証を8項目で整理する「章の論証契約」．
- 英文変換，模擬査読，内容補強，章の深掘り・肉付け，校正，文献調査のためのAIプロンプト作成．
- 章本文，章別指示，著者，参考文献，図・表・データのブラウザー内編集．
- BibTeXの読込み，Typst・BibTeX・Hayagriva YAMLの書出し．
- ブラウザー印刷によるPDF保存，JSONバックアップ，添付を含むZIPバックアップと復元．
- 招待制のメールOTPログインと，版番号で上書きを防ぐ任意の端末間同期．

外部AIへ自動接続しない．クラウド同期を設定していない場合，入力内容は端末内で処理する．同期を有効にした場合も，ログインと利用者の同期操作なしに原稿をアップロードしない．生成器は未入力の数値や参考文献を補完せず，確認が必要な箇所を明示する．

## 章立てと章の論証契約

編集画面の「章構成」では，章を追加し，見出しを変更し，順序を入れ替えて論文全体の流れを整理できる．プロジェクト全体の中心研究課題を入力したうえで，各章について次の8点を記録できる．

1. この章が解く問題は何か？
2. 既存研究（または前章）では何が不足しているか？
3. その不足に対して何を提案したか？
4. どの仮説を検証するか？
5. どの実験・解析が仮説を支えるか？
6. 結果から何がいえるか？
7. 何は言えないか？（Limitは何か？）
8. 博士論文全体の中心研究課題に対して，この章はどの一文で答えるか？

ここでいう「論証契約」は，章内の問題・提案・証拠・結論・限界を対応付けるための執筆メモである．法的な契約，研究倫理上の承認，査読済みの判断，検証済み証拠を意味しない．記入しただけで仮説や結果の妥当性が確認されたことにはならない．

論証契約は章本文とは別に保存する．草稿の再生成，Typst書出し，ブラウザー印刷へ自動挿入せず，著者が確認して本文へ反映する．通常はブラウザー内だけに保存され，任意のクラウド同期を設定してログインし，対象プロジェクトの同期を明示的に実行した場合だけ，そのプロジェクトの一部としてSupabaseへ保存される．JSON／ZIPバックアップには復元用データとして含まれる．

## テンプレートを登録する

1. 左メニューの「テンプレート」を開く．
2. 「ファイルを選んで登録」からテンプレートを選ぶ．
3. 自動解釈された構成の「この構成で作る」を押す．

見出し，主な言語，1段組／2段組，必要な研究情報をブラウザー内で解釈する．対応形式はJSON，Markdown，TXT，Typst，LaTeX，HTMLで，上限は512 KiBである．元ファイルやHTMLコードは保存せず，安全に正規化した構成定義だけを登録する．PDFとDOCXは構造を正確に解釈できないため，テキスト形式へ変換してから登録する．

## AIプロンプト作業台を使う

1. 論文プロジェクトを作成し，本文または研究情報を入力する．
2. 左メニューの「AI作業台」で，英文変換，模擬査読，内容補強，章の深掘り・肉付け，校正，文献調査から用途を選ぶ．章の編集画面から対象章を指定して開くこともできる．
3. 作成されたプロンプトを確認し，必要な箇所だけをコピーまたはテキスト保存する．

作業台はAIを実行せず，APIキーを保存せず，OllamaやQwenにも自動接続しない．使用先に合わせた指示文を作るだけである．ローカルLLM，Codex，Claude Codeなどへ貼り付けるかどうか，どの情報を渡すかは利用者が決める．「貼り付けた範囲だけ」や「1つのセクション」を選んだ場合は，選択外の原稿・著者・参考文献・研究情報をプロンプトへ含めない．プロンプトには，未確認の事実・数値・文献を作らない条件と，結果を確認しやすい返答形式を含める．

章の深掘りでは，対象章の本文，その章の論証契約，論文全体の中心研究課題だけを資料データとして使う．別章や添付ファイルを自動で含めず，不足する根拠は創作せず確認質問として出す．作成された文章案も検証済みの成果ではないため，著者が元データ・文献・解析結果と照合してから採用する．

### GitHub Pagesで使う

GitHub Pagesを有効にした場合は，公開されたURLをブラウザーで開くだけで利用できる．初回は次の順で手動公開する．

1. GitHubのリポジトリで `Settings` → `Pages` を開く．
2. `Build and deployment` の `Source` を `GitHub Actions` にする．
3. `Actions` → `Deploy static app to Pages` → `Run workflow` を開く．
4. 公開対象のブランチ（通常は `main`）を選び，`Run workflow` を押す．
5. 完了後，ワークフローまたは `Settings` → `Pages` に表示されたURLを開く．

このリポジトリにはPages配信用ワークフローを含むが，本READMEはデプロイ済みであることを保証しない．

## 端末間同期を使う（任意）

端末間同期は，GitHub PagesなどのHTTPS版とSupabaseを組み合わせる．利用者の端末にはPythonやサーバー構築は不要で，メールに届くワンタイムコードでログインする．管理者だけが最初にSupabaseプロジェクトと公開用接続情報を設定する．

- ブラウザーへ置くのはPublishable keyだけとし，Secret keyや`service_role` keyを置かない．
- 全データをRLSで本人のアカウントに限定し，添付は非公開Storageへ保存する．
- 初回ログインで端末内データを自動送信せず，プロジェクトごとにクラウドへコピーする．
- 端末版とクラウド版が両方変更されていた場合，自動上書きせず競合として停止する．
- クラウド上のプロジェクト形式より古い`schemaVersion`のクライアントは，版番号が一致していても保存できず競合として停止する．
- `index.html`をダブルクリックした`file://`版は，従来どおり完全な端末内モードとして使う．
- 初期版ではクラウド添付を不変オブジェクトとして扱い，端末側で添付を外してもStorage本体を自動削除しない．機密データの削除は管理者が確認して行う．

初期設定は [クラウド同期の初期設定](docs/cloud-sync-setup.md) を参照する．未発表原稿や個人情報を保存する前に，所属組織が外部クラウドを許可しているか確認すること．

GitHub Pagesではリポジトリのパスが違っても，同じ`USER.github.io`ホスト上のサイトは同じブラウザー保存領域を共有する．機密原稿には本アプリ専用のカスタムドメイン，または本アプリ専用のGitHubアカウント／Organizationを推奨する．ログアウトしても端末内コピーは削除・暗号化されない．

## データ保存とバックアップ

編集内容と設定は，まず利用中のブラウザー内ストレージへ保存される．クラウド同期が未設定，未ログイン，または利用者が同期を実行していない状態ではサーバーへ送信されない．重要な原稿は，クラウド同期の有無にかかわらず画面からバックアップを定期的に保存すること．本文・設定だけならJSON，添付した図・データを含む完全な復元にはZIPを使う．バックアップの上限は100 MBであり，添付本体がブラウザー内に残っていない場合は不完全なZIPを作らず，画面にエラーを表示する．Typstソースは `.typ` または添付込みZIPとして書き出せる．

次の環境は別々の端末内保存領域として扱われる．任意のクラウド同期を設定しない限り，内容は共有されない．

- ダブルクリックで開いた `file://` 版とGitHub Pages版
- 異なるブラウザー，ブラウザープロファイル，PC
- 通常ウィンドウとプライベートブラウジング

別の環境へ移る前にバックアップを作成する．JSONとZIPはどちらも「バックアップを読み込む」から復元できるが，JSONに添付ファイル本体は含まれない．ZIPでは添付した図・データも再接続される．ブラウザーデータを消去すると，クラウドへ同期していない内容は失われる可能性がある．

## PDFとTypst

- 画面の原稿をPDFにする場合は，ブラウザーの印刷機能から「PDFに保存」を選ぶ．
- ブラウザー印刷へ埋め込む図表はPNG，JPEG，SVGを使う．PDF形式の図表はPNG/SVGへ変換するか，Typst ZIPから組版する．
- Typstソースは書き出せるが，本アプリはTypstコンパイラーを実行しない．必要に応じて書き出した `.typ` を別のTypst環境でコンパイルする．

## プライバシー

主要機能は静的ファイルだけで動作する．公開された静的JavaScriptでは秘密鍵を安全に秘匿できないため，OpenAI互換APIなどへのライブ接続と秘密のAPIキー保存は実装しない．任意のSupabase同期ではブラウザー用Publishable keyと本人限定RLSを使用し，管理者用キーを拒否する．LLMなしで使えるルールベース支援と，利用者が確認して持ち出すプロンプト生成を基本とする．

詳しくは [プライバシーと制約](docs/privacy-and-limitations.md) を参照する．

## GitHub Pages

`.github/workflows/pages.yml` は，`main`へのpushまたは手動実行でPagesへ配信する．利用前にGitHubのSettingsからPagesのSourceを「GitHub Actions」に設定する．ワークフローにアプリのビルド処理はなく，テスト後に静的ファイルをそのまま配信する．

## 開発

HTML，CSS，JavaScriptを編集し，`index.html`を再読込して確認する．実行環境の構築コマンドはない．設計は [アーキテクチャ](docs/architecture.md) を参照する．

ブラウザーだけでテストする場合は，`tests/index.html` をダブルクリックする．GitHub Actionsでは同じロジックテストに加え，章立てと論証契約，テンプレート解釈，図・データ診断，AIプロンプト生成，端末保存，クラウド同期，RLSスキーマ，公開設定，`file://` 起動をNode.jsとヘッドレスブラウザーで確認するが，アプリの利用者にNode.jsは不要である．
